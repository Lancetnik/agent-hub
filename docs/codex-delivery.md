# Доставка сообщений в существующую сессию Codex

Постоянный внешний клиент `scripts/codex_session.py` связывает входящие Hub
с одним thread Codex App Server. Пользователь запускает клиент и выбирает
стабильный адрес Hub. Сервер Hub никогда не запускает runtime или worker.

Для обычного интерактивного `codex` используйте [интеграцию через хуки](codex-hooks.md):
она подключается к уже запущенному CLI, автоматически регистрирует его и сохраняет
управление в CLI. Ниже описан отдельный внешний stdio-клиент.

## Подтверждённый интерфейс

Проверка `scripts/check_codex_input.py` на Codex CLI 0.162.1 отправила два
реальных хода в один thread: первый запомнил число 37, второй прибавил 5
без повторной передачи числа и вернул 42. Идентификаторы и статус принятия
сохранены в [codex-input.json](evidence/codex-input.json).

[Официальный контракт App Server](https://learn.chatgpt.com/docs/app-server)
описывает `thread/resume`, `turn/start`, `turn/completed` и stdio transport.
Адаптер использует `turn/start` с существующим `threadId`, сохраняет полученный
`turn.id` и отправляет ACK. Терминальное событие описывает результат хода;
успех задачи оценивает оркестратор. `turn/steer` здесь не используется:
входящие ждут завершения занятого хода.

## Серверный контракт

- `GET /sessions/{session_id}/events`: `text/event-stream`, события
  `inbox_changed` с пустым JSON `{}`. Первое событие приходит при каждом
  подключении. Новые и повторно отправленные неподтверждённые сообщения дают
  сигнал после записи в SQLite. Keepalive раз в две секунды позволяет клиенту
  проверять входящие при отсутствии событий. Неизвестная сессия даёт HTTP 404.
- `GET /sessions/{session_id}/inbox?limit=100&cursor=...`: прежний контракт
  MCP inbox, включая порядок, исключительный курсор, только неподтверждённые
  записи и `next_cursor`. Каждый новый просмотр начинается без курсора.
- `POST /sessions/{session_id}/ack`, тело `{"message_id":"..."}`: прежний
  идемпотентный ACK с проверкой адресата. Чтение и SSE не подтверждают сообщение.

Эти HTTP endpoints используют те же таблицы и операции, что MCP tools.
SSE не хранит историю событий и не несёт payload. После обрыва, потери сигнала
или переполнения очереди клиент снова читает durable inbox. Идентификатор
сессии в URL нужно кодировать как один компонент пути.

## Состояние внешнего клиента

`--state` — отдельная SQLite-база каждой сессии. В ней хранятся адрес Hub,
thread ID, принятые сообщения с соответствующими turn ID, состояние ACK
и outbox результатов. Одновременно использовать один файл может только
один процесс: файл блокируется на время работы.

При первом запуске клиент создаёт постоянный thread, сохраняет ID и регистрирует
его в Hub. Повторный запуск возобновляет этот thread. Стартовый prompt выполняется
только при создании; повторный запуск команды не отправляет его заново.
Каждое входящее передаётся в контекст целиком, включая `message_id`, отправителя
и корреляцию. Если текущий ход занят, сообщение остаётся в inbox без ACK.

После ответа `turn/start` клиент сначала фиксирует локальную запись принятия,
затем подтверждает приём в Hub. При потере ответа ACK его повтор использует
эту запись. Пока подтверждение не доставлено, адаптер не принимает следующий
входящий запрос. Результаты runtime обрабатываются независимо от ожидания ACK.

Worker с `--report-results` сохраняет результат завершённого входящего хода
в локальную outbox, адресуя его отправителю принятого сообщения. Сохраняет
`correlation_id` или использует `message_id`, если корреляция отсутствовала.
Статусы `failed` и `interrupted`, nullable текст и runtime error передаются
так же, как в одноразовом адаптере третьего этапа. Сохранённые HTTP-события
повторяются автоматически. При возобновлении thread клиент читает сохранённые
turn/items, чтобы восстановить пропущенные терминальные результаты принятых ходов.

## Проверки и воспроизведение

```sh
python3 scripts/check_codex_input.py --output /tmp/codex-input.json
python3 scripts/check_codex_delivery.py --output /tmp/codex-delivery.json
```

Полное демо создаёт две настоящие сессии: оркестратор выбирает MCP tool
и отправляет поручение; worker завершает ход без completion tool; оркестратор
автоматически начинает новый ход в прежнем thread и использует число,
запомненное в первом ходе. Три сценария: свободная сессия, занятая сессия
с результатом в неподтверждённых входящих, отключение адаптера и аварийный
перезапуск Hub с возобновлением исходной сессии. Результаты: 41, 43, 45.
Захват событий: [codex-delivery.json](evidence/codex-delivery.json).

HTTP/MCP-тест проверяет SSE-сигналы, курсоры, общий ACK, повторное подключение
и сохранение сообщений после переоткрытия базы. Python-тесты проверяют отказ
runtime без ACK, ожидание занятого хода, потерю ответа ACK и повтор после
перезапуска без второго хода, восстановление результата и защиту идентичности.

## Границы доставки

- Этот клиент владеет одним stdio App Server и его thread. Подключение
  к обычному CLI реализовано отдельной [интеграцией через хуки](codex-hooks.md).
  Thread внешнего клиента можно
  возобновить при перезапуске этого внешнего клиента. Одновременное управление
  из другого UI не поддерживается; один Hub-адрес должен иметь одного владельца
  и один файл состояния.
- Между ответом runtime и фиксацией локальной записи принятия есть окно аварии.
  После аварии или потери RPC-ответа сообщение может попасть в повторный ход.
  Это доставка с возможными повторами, без гарантии exactly-once исполнения.
  Принимающие задачи должны учитывать `message_id` при внешних побочных эффектах.
- ACK означает принятие runtime. Последующая ошибка, прерывание или авария
  runtime не возвращают принятое сообщение в inbox. Worker сообщает терминальный
  результат, когда он доступен в событиях или сохранённой истории. Если runtime
  не сохранил терминальный результат, адаптер не выдумывает его.
- Новые регистрации и истории Codex сохраняются; автоматической очистки нет.
  Локальный журнал также растёт. Не удаляйте state/thread history для сессии,
  которую нужно возобновить. Потеря стартового prompt в окне аварии после создания
  thread требует явного нового сообщения; автоматического повтора prompt нет.
- Прототип использует `read-only` sandbox и `approvalPolicy: never`, отклоняет
  интерактивные input/approval-запросы и наследует конфигурацию установленного
  Codex. Сессии продолжаются по модели и настройкам этого Codex.
- `--report-results` включают для worker, который отвечает на каждое входящее.
  Для оркестратора флаг по умолчанию выключен, чтобы автоматические ответы
  на результаты не порождали бесконечный обмен.
- SSE и HTTP доступны доверенным локальным интеграциям без аутентификации.
  Для восстановления нужны сохранённая база Hub, state адаптера и история Codex.
  Остановка адаптера закрывает его App Server; выполняющийся ход может прерваться.
